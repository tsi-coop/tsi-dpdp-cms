# Security Fix 4: API Parameter Schema Enumerable Without Authentication

## Issue

TSI-DPDP-CMS-API-Parameter-Schema-Enumerable-Without-Authentication

**Class:** Exposure of Sensitive Information (CWE-200), Missing Authorization
(CWE-862)

## Reported By

VulDB, received 2026-10-02. Originally discovered by Kavin Kumar S T
(2026-07-10).

## Description

The API dispatcher validated the request payload against its JSON schema
*before* checking authentication. An unauthenticated caller who sent a valid
`_func` with required fields omitted received a `400` that named every
missing field, e.g.:

```
{"error": "[$: required property 'fiduciary_id' not found]"}
```

By supplying fields one at a time and reading the `400` responses, a caller
with no credentials could map the full parameter schema of every `_func`
on the admin and DPO APIs - including `/api/v1/admin/job`,
`/api/v1/admin/apikey`, `/api/v1/admin/operator` and `/api/v1/dpo/ropa` - and
learn details of the internal data model (for example, that `fiduciary_id`
scopes every operation).

Confirmed against the code: in `InterceptingFilter.doFilter`,
`InputProcessor.validate(req, res)` ran before any of the per-category auth
branches and before the `if (!authenticated)` check, and `validate` returned
the schema validator's error set verbatim to the client. The same ordering
applied to the client API (`/api/v1/client/*`), which the report did not list.

**Severity: Low, as reported** (CVSS 3.1 score 3.1,
`AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N`). The leak is limited to field names;
it exposes no data and grants no access by itself. It lowers the cost of
crafting requests against the authenticated surface, which is still protected
by authentication and per-tenant authorization.

**Correction to the original report:** the report states the issue was fixed
in v0.5.1. That is inaccurate. v0.5.1 fixed the reporter's two related
findings ([1](1.md), [3](3.md) for the console pages and [2](2.md) for the
bootstrap endpoint) but did not change the validate-before-auth ordering. The
ordering is identical in v0.5.0, v0.5.1 and v0.5.2, and dates back to a
2025-07-28 commit. **Affected: v0.5.2 and earlier. Fixed in v0.5.3.**

## Our Fix

1. **Authentication now runs before payload validation**
   (`src/org/tsicoop/dpdpcms/framework/InterceptingFilter.java`) - the
   `InputProcessor.validate()` call was moved from the top of `doFilter` to
   immediately after the `if (!authenticated)` → `401` block. A missing or
   invalid token now returns `401 Unauthorized` before any schema validation
   runs, so no field names are disclosed. Authenticated callers, and the
   functions that are unauthenticated by design (`ADMIN_NOAUTH_FUNCS`, the
   bootstrap `setup` service, the public `_func` whitelist), still get the
   same `400` validation behavior as before.
2. **Same ordering applied to the client API** - the move is in the shared
   dispatcher path, so `/api/v1/client/*` requests with a missing or invalid
   API key/secret or principal token also get `401` first.

**Verified live** (built the WAR from the working tree, ran it against a
freshly initialized Postgres, and compared against the published v0.5.2
image):
- Unauthenticated, and invalid-token, `POST` of each `_func` below with no
  other fields → `401`, no field names - **16/16** requests on the fixed
  build. The same requests against the published v0.5.2 image returned `400`
  with field names on **14/16**: `/api/v1/admin/job` (`list_jobs`,
  `create_job`), `/api/v1/admin/apikey` (`list_api_keys`,
  `generate_api_key`), `/api/v1/admin/operator` (`create_user`) and
  `/api/v1/admin/ropa` (`list_entries`, `create_entry`). `list_users` already
  returned `401` on v0.5.2.
- With a valid admin token and required fields omitted, `create_job`,
  `list_jobs`, `list_api_keys` and `create_entry` → `400` naming the missing
  fields, so validation still works for authenticated callers.
- Client API (`/api/v1/client/consent`, `get_active_consent`, `user_id`
  omitted): no key, unknown key, and real key with wrong secret → `401`; valid
  key and secret → `400` naming `user_id`. On v0.5.2 the first two returned
  `400` naming `user_id`.
- Unauthenticated-by-design functions (`initial_setup`,
  `request_principal_otp`, `login`, `reset_password`) with fields omitted →
  still `400`, as before.
- The authenticated setup path used to run the checks (bootstrap, login,
  create Fiduciary, App and API key) worked unchanged.

**Note on the report's endpoint names:** the report lists `/api/v1/dpo/ropa`,
`create_api_key`, `list_operators` and `create_operator`. In this codebase the
routes are `/api/v1/admin/ropa`, `generate_api_key`, `list_users` and
`create_user`; `/api/v1/dpo/ropa` returns `404`. The underlying behavior is
the same on the real routes.

**Found but out of scope, not fixed here:**
- The dispatcher calls `inputJson.get("_func")` before its
  `inputJson == null` check, so an empty or invalid body throws an
  unhandled exception and returns `500`.
- The catch-all `500` handler echoes `e.getMessage()` to the caller,
  including unauthenticated callers.

Neither was part of the report; both are left for a separate ticket.
