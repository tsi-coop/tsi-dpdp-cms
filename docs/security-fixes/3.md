# Security Fix 3: Missing Authentication on All Admin and DPO Console Pages

## Issue

TSI DPDP CMS - Missing Authentication on All Admin and DPO Console Pages

**Class:** Missing Authentication for Critical Function (CWE-306)
**Secondary class:** Exposure of Sensitive Information to Unauthorized Actor (CWE-200)

## Reported By

VulDB, received 2026-08-24.

## Description

All 17 admin and DPO console pages (`/console/admin/*.html`,
`/console/dpo/*.html`) were served with HTTP 200 to any HTTP request, with no
server-side authentication check - only client-side JavaScript reading
`localStorage.getItem('authToken')` and redirecting the browser if absent, a
control any non-browser client (curl, wget, scripted requests) simply
ignores.

This is the same underlying root cause as [Security Fix 1](1.md): `InterceptingFilter`,
the app's only auth-enforcing servlet filter, was mapped in `web.xml` to
`/api/*` only, so every static console page fell through to unauthenticated
static file serving. This report frames it primarily as CWE-306 (missing
auth on the pages themselves) with CWE-200 (source/API-contract exposure)
as the consequence, rather than CWE-602 as the primary class - same root
cause, different framing/title, resubmitted separately.

Unlike the [Security Fix 1](1.md) submission, this report's impact section
is already accurately scoped - it explicitly notes "the API endpoints
themselves require a valid Bearer token (returning HTTP 401 without one)"
and correctly characterizes the impact as attack-surface disclosure (API
endpoint paths, `_func` dispatch values, request schemas, token/localStorage
format, role-routing logic) rather than claiming direct access to data or
operations. No severity correction is needed here.

## Our Fix

No additional fix required - fully covered by the work already done for
[Security Fix 1](1.md):

- `ConsoleAuthFilter` (`src/org/tsicoop/dpdpcms/framework/ConsoleAuthFilter.java`)
  gates `/console/admin/*` and `/console/dpo/*` server-side, requiring a
  valid, non-revoked operator session (`JWTUtil.isTokenValid()`) before any
  of the 17 pages is dispatched, redirecting to `/index.html` otherwise.
- The session cookie enabling this (`console_session`, `HttpOnly;
  SameSite=Strict; Secure`) is set at login and cleared at logout via
  `InputProcessor.setConsoleSessionCookie` / `clearConsoleSessionCookie`,
  independent of and additive to the existing bearer-token API auth flow.
- Verified still intact at the time of this report's triage (2026-08-24):
  `ConsoleAuthFilter`, its `web.xml` mappings, and the login/logout cookie
  wiring in `Operator.java` are all present and unchanged since Fix 1
  shipped.
- Live-tested during the original fix (see [1.md](1.md)): the exact PoC in
  this report (unauthenticated GET across all 17 paths) now returns a
  redirect instead of HTTP 200 with page content; authenticated GET (with
  the session cookie set at login) returns 200 as expected.

See [1.md](1.md) for the full root-cause analysis and the complete list of
files changed.
