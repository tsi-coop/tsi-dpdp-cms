# Security Fix 2: Unauthenticated Super-Admin Bootstrap Endpoint

## Issue

TSI-DPDP-CMS-Unauthenticated-Super-Admin-Bootstrap-Endpoint

**Class:** Missing Authentication for Critical Function (CWE-306)

## Reported By

VulDB, received 2026-08-24.

## Description

The Super-Admin bootstrap endpoint (`POST /api/v1/bootstrap/setup`, `_func:
"initial_setup"`) and its setup wizard (`/console/setup/init.html`) were
reachable by any unauthenticated HTTP client. On a fresh deployment or after
a database reset, a single POST with attacker-chosen `email`/`name`/`password`
created a fully privileged Super Administrator account - complete control of
the application, with no prior credentials required.

The only server-side guard was a state check
(`AdminSetup.isAdminUserExists()` - "is there already an ADMIN row?"). That's
not an authentication control: it protects nothing on a fresh deployment,
after a re-deploy, or after any DB state reset, which is exactly the window
an attacker races to win.

Confirmed against the code:
- `InterceptingFilter.java:305-309` explicitly allows the bootstrap path
  through with no auth: `authenticated = "setup".equalsIgnoreCase(serviceName);`
- `AdminSetup.java` created the operator row directly off `isAdminUserExists()`
  returning `false`, with no credential of any kind checked.
- `/console/setup/init.html` had no pre-load check and rendered a working
  form to anyone, indefinitely (not just during the bootstrap window).

**Severity: Critical, as reported** - unlike the console-auth finding
([1](1.md)), there is no independent authentication layer behind this
endpoint; a won race is a genuine full takeover, and the realistic
exploitation window (a container reachable before the operator finishes
clicking through setup) is real for internet-facing deployments.

**Two additional issues found during verification, not in the original
report:**
- **Directory listing on `/console/setup/`** - the report's PoC claimed this
  and it checks out: this app runs on stock Jetty
  (`Dockerfile: FROM jetty:jdk17`), and Jetty's bundled
  `webdefault-ee10.xml` (merged into every webapp ahead of this project's
  `web.xml`) hardcodes `dirAllowed=true`. Confirmed by extracting that file
  from the actual image; this app never overrode it.
- **A latent response-code bug**: `AdminSetup.java` compared
  `"System is already configured.".equals(result.get("error"))` against a
  stored string that actually read
  `"System is already configured. Cannot run initial setup."` - the mismatch
  meant the "already configured" case always fell through to 500 instead of
  the intended 409. Not itself a security hole, but fixed alongside since it
  was in the same code path.

## Our Fix

1. **Required setup token** (`src/org/tsicoop/dpdpcms/service/v1/AdminSetup.java`)
   - `initial_setup` now requires a `setup_token` field matching the
   `TSI_BOOTSTRAP_TOKEN` environment variable, compared with
   `MessageDigest.isEqual` (constant-time). There is no built-in default or
   fallback: if `TSI_BOOTSTRAP_TOKEN` is unset on the server, the endpoint
   refuses every request with 503 rather than falling back to open access -
   fails closed. The token check runs before any database access, so a
   caller without the token learns nothing about whether the system has
   already been configured. `web/WEB-INF/validator/initial_setup.jschema`
   was updated to require the new field, and `web/console/setup/init.html`
   gained a "Setup Token" input so the UI stays usable for a deployer who
   knows the token.
2. **Directory listing disabled** - `web.xml` now redeclares the `default`
   servlet (`org.eclipse.jetty.ee10.servlet.DefaultServlet`) with
   `dirAllowed=false`, overriding Jetty's bundled default for this webapp.
   Welcome-file resolution (e.g. `/console/` → `/console/index.html`) is
   unaffected since it's tried before the listing fallback.
3. **Fixed the 409 mapping** - `performInitialSetup` now returns an explicit
   `already_configured` flag instead of relying on exact-string matching, so
   re-running setup after the system is initialized correctly returns 409.
4. **Closed the TOCTOU race as defense-in-depth** - the existence check and
   the insert now run inside a single `SERIALIZABLE` transaction. If two
   requests both observe an empty `operators` table, Postgres aborts the
   loser (SQLState `40001`) instead of letting both create an account. The
   connection's isolation level is reset before it's returned to the pool.

**Verified live** (built the actual WAR from the project's own `Dockerfile`,
ran it against a fully migrated Postgres instance):
- No `TSI_BOOTSTRAP_TOKEN` configured → `POST /api/v1/bootstrap/setup` → 503,
  no account created.
- Wrong `setup_token` → 401, no account created - this is the exact
  unmodified PoC payload from the report.
- Correct `setup_token` → 201, account created.
- Re-running setup afterward → 409 (confirms the response-code fix).
- `GET /console/setup/` → 403, not a directory listing; `/console/setup/init.html`
  and `/console/` welcome-file forwarding still work normally.
- Composes correctly with the console-auth fix ([1](1.md)): logging in with
  the new admin account sets the `console_session` cookie, and console pages
  gate/allow access as expected.

**Found but out of scope, not fixed here:** there is no
`web/WEB-INF/validator/logout.jschema`, so `_func: "logout"` has likely never
passed schema validation on `/api/v1/admin/operator`. Discovered while
verifying this fix; unrelated to either reported vulnerability and left for
a separate ticket.
