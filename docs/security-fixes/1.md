# Security Fix 1: Client-Side-Only Authentication on Console Pages

## Issue

TSI-DPDP-CMS-Client-Side-Only-Authentication-Allows-Complete-Bypass-via-Direct-HTTP-Request

**Class:** Client-Side Enforcement of Server-Side Security (CWE-602)
**Secondary class:** Missing Authentication for Critical Function (CWE-306)

## Reported By

VulDB, received 2026-08-24.

## Description

All 17 admin and DPO console pages (`/console/admin/*.html`, `/console/dpo/*.html`)
were served with HTTP 200 to any HTTP request, with no server-side authentication
check. The only login gate was client-side JavaScript:

```js
const AUTH_TOKEN = localStorage.getItem('authToken');
if (!AUTH_TOKEN) {
    window.location.href = '../index.html';
}
```

This check runs in the browser only, after the full page has already been
delivered. Any client that doesn't execute JavaScript (curl, wget, Python
requests, Burp Suite, etc.) received the complete page source unauthenticated,
including internal API endpoint paths, `_func` dispatch values, request
parameter schemas, and the admin/DPO role-routing logic.

Root cause: `InterceptingFilter`, the app's only auth-enforcing servlet filter,
was mapped in `web.xml` to `/api/*` only. Any request outside that prefix —
including every static console page — bypassed it entirely and fell through to
default static file serving.

**Severity correction:** the original report characterized this as a "complete
bypass" enabling unauthenticated access to admin/DPO functionality. That
overstates impact — every API call the console pages make
(`/api/v1/admin/*`, `/api/v1/client/*`) is independently authenticated
server-side on each request via `InterceptingFilter` /
`InputProcessor.processAdminHeader`, regardless of whether the page's
client-side check ran. No ROPA, breach, grievance, or user data, and no
`_func` operation, was reachable via this issue without valid credentials.
Actual impact was disclosure of client-side application source (endpoint
list, `_func` names, request schemas) — classified as **Medium —
Information Disclosure**, not Critical.

## Our Fix

Added a server-side gate in front of the console pages, independent of the
existing (unaffected) API authentication:

- **`ConsoleAuthFilter`** (new, `src/org/tsicoop/dpdpcms/framework/ConsoleAuthFilter.java`)
  — a servlet filter mapped to `/console/admin/*` and `/console/dpo/*` in
  `web.xml`, dispatched on `REQUEST` and `FORWARD`. It runs before any static
  file is dispatched and requires a valid, non-revoked operator session
  (validated via the existing `JWTUtil.isTokenValid()`) or redirects to
  `/index.html` instead of serving page content.
- **Session cookie** — a plain browser navigation to a URL cannot carry a
  custom `Authorization` header (only `fetch`/`XHR` calls can), so a
  short-lived `HttpOnly; SameSite=Strict; Secure` cookie
  (`console_session`, scoped to `/console`) is set at login and cleared at
  logout:
  - `InputProcessor.setConsoleSessionCookie` / `clearConsoleSessionCookie`
    (new, `src/org/tsicoop/dpdpcms/framework/InputProcessor.java`) — built as
    a raw `Set-Cookie` header since the project's Servlet 5.0 API predates
    `Cookie.setAttribute("SameSite", ...)`. `Secure` is omitted only when
    `TSI_DPDP_CMS_ENV=local`, matching the existing local/prod TLS convention
    in `PoolDB.java`.
  - `Operator.handleLogin` sets the cookie alongside the existing token
    response; `Operator.handleLogout` clears it, next to the existing
    JWT blocklist revocation.
- This is purely additive to the existing bearer-token flow the console JS
  uses for its own API calls (`localStorage` + `Authorization: Bearer`) —
  that flow, and the API-side authentication it relies on, is unchanged.

**Result:** an unauthenticated request (curl, no session cookie) to any of the
17 console pages now receives a redirect to `/index.html` instead of page
content.
