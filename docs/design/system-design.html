1. Introduction and positioning

TSI DPDP CMS is an open-source (Apache 2.0) consent management system for India's Digital Personal Data Protection Act, 2023. One codebase serves two kinds of adopter:

AdopterPositioningMode
Data FiduciaryDeploys the CMS itself to manage consent for its own Data Principals, without depending on a third party. Consent, rights, erasure and breach records stay within the organisation.Single mode: one fiduciary, the Data Fiduciary and Consent Manager are the same entity.
Consent Manager / Consent AggregatorDeploys the CMS as a managed service that manages consent on behalf of one or more Data Fiduciaries, each as an isolated tenant with its own policies, API keys, operators and data.Aggregator mode: many fiduciaries, distinct parties as in the data flow diagram.

Either can use it out of the box. System integrators can extend it for larger organisations or other jurisdictions.

This is a tool for technology teams. It is not suitable for business teams to use directly. Deploying it, wiring it into applications (consent capture, validate_consent, purge handling, webhooks), setting secrets and TLS, and compiling a policy and RoPA all need engineers. The consoles are for the DPO and operators after technical teams have integrated and configured it. The bundled rights portal is an evaluation aid for implementers, not a product for data principals. Business and legal teams should expect to work through their technology team or an integrator.

Audience: architects, developers, DevOps, QA, and technical project owners; DPOs and reviewers as consumers of the consoles. Out of scope: the fiduciary's own applications and databases. The CMS records consent and tracks obligations; it does not store the principal's personal data values.

3. Architecture

3.1 Big Picture

The Data Fiduciary System (DFS) collects consent through the Consent Manager (CM) (1) before receiving data (2). The DFS validates consent with the CM (3) before sending data (4) to a Data Processor (DP). The DP processes and informs the CM (5). When the principal modifies or withdraws consent, the CM notifies the DFS and DP to limit or delete the data (6). The DPO produces a report for the Data Protection Board (7).

In single mode the DFS and CM are the same deploying entity: the interaction is an internal module boundary. In aggregator mode they are distinct parties, as drawn.

3.2 Architecture (conceptual)

The conceptual services map onto one deployable: policy, consent, data principal, grievance and regulatory reporting (breach and Board intimation); notification, fiduciary and processor (fiduciaries and Apps), audit, retention and purge (the CES and Compliance), and admin (operators and roles). 3.5 Key design decisions

  • Monolith by choice. One WAR, one PostgreSQL. Simple to run for an MSME; horizontal scale needs only a shared database and the (30 s) policy cache already tolerates several instances.
  • Function-dispatch API. POST /api/v1/{admin|client|public}/{service} with a JSON _func. Each function has a JSON schema and a permission entry; authentication runs before validation.
  • Policy is the source of truth. Consent records point to an exact policy version; a policy goes live only when its RoPA activities are approved.
  • Append, never overwrite. New consent supersedes the old record, and the audit ledger refuses updates and deletes.
  • The CMS does not hold personal data values. It records identifiers (opaque principal IDs), decisions, evidence and obligations.

4. Functional design

4.1 Setup, access and tenants

  • First run: admin setup screen guarded by a one-time TSI_BOOTSTRAP_TOKEN; fails closed if unset.
  • Operators and roles: ADMIN (platform, all tenants), DPO and OPERATOR (one fiduciary), AUDITOR (read-only). A permission (resource:read|write|manage) is checked on every function; a non-ADMIN sees only their own fiduciary. Refusals are audited as ACCESS_DENIED.
  • Login: password plus TOTP authenticator (mandatory in production for ADMIN, DPO, AUDITOR); replay-proof codes, lock-out on repeated failure; 8-hour sessions with revocation; break-glass recovery by master recovery key.
  • Fiduciaries and Apps: a fiduciary is a tenant. Apps (the DF's own systems and processors) get API keys with a scope of READ, WRITE or PURGE, optional expiry and revoke. Optional DNS TXT proof of domain ownership; it is a credibility signal and gates nothing. Deactivation takes effect immediately.
  • Modes: single (one tenant) or aggregator (many); same code, different data.

4.2 Policy and RoPA

  • A policy is versioned, multilingual JSON: purposes (id, legal basis, data categories, recipients, retention, mandatory/sensitive flags), data categories, rights summary, grievance contact. States: DRAFT, ACTIVE, ARCHIVED.
  • Each purpose has a RoPA activity, derived from the policy and completed by the DPO (accountability fields, retention, processors). Completeness is validated. Approve per activity or all at once; when all are approved the policy goes live and the previous version is archived. Only one live version per policy (database-enforced).
  • Active policies are immutable; change means a new version. Policies are cached for at most 30 s across instances. RoPA exports to CSV.
  • Purpose lifecycle: the DPO can close a purpose (consents withdrawn, new grants refused, data erased) via a guided flow that publishes a policy version without it, and reopen it later.

4.4 Data Principal rights and grievances

  • Access and correction (s.11, s.12): request, assign, outcome note, optional deadline. The CMS tracks the request; it holds no personal data values.
  • Nomination (s.14): a nominee is stored encrypted and masked for the DPO; no access is granted.
  • Grievances (s.13): reference GRV-year-nnnnnn, channel, link to a consent record, validated attachments, DPO assignment, status workflow, principal feedback.
  • Principal login: OTP (email or mobile) with rate limits. The placeholder OTP mode is refused in production. The bundled portal is an evaluation tool; real principals use the DF's own application.

4.5 Erasure, retention and legal holds

  • Purge states: PURGE_INITIATED → IN_PROGRESS → COMPLETED | FAILED, plus CANCELLED and LEGAL_HOLD_APPLIED. Completed and cancelled are final.
  • Apps collect purges by polling and/or webhook, and confirm with update_purge_status. A key may confirm only purges assigned to its own App; the confirmer is taken from the credential. The record count is shown as a processor claim, not verified. Manual handling is available to the DPO.
  • Legal hold: the DPO places a time-bound hold (max 730 days) with a written reason; affected purges are deferred and resume automatically when it ends. A processor can report its own legal obligation to keep data; this is recorded and shown but does not suspend the purge.
  • Optional deadlines (PURGE_COMPLETION_SLA_DAYS etc.) are unset by default: nothing is flagged overdue until configured. Purges not picked up within 24 h are tagged.

4.6 Breach management (s.8(6))

  • Report, assess and contain a breach, scoped to the affected policy and purpose; affected principals resolved automatically or by CSV upload.
  • Principal notice deadline: detection + 72 h (DPO-configurable down to 1 h), with countdown and overdue state. Board deadline tracked from report; the DPO records when and under what reference the Board was informed, with one alert when near and one when missed.
  • Two PDFs per incident: Information report and Action report (interim version while open). Notification log with sent text and read status.

4.7 Audit and evidence

  • Audit ledger: every significant action; each row's hash covers all stored columns and chains to the previous; the database blocks updates, deletes and truncation; a daily job verifies the chain and stores the result.
  • Evidence certificate: a signed (PKCS12) attestation over an audit segment with system metadata and software version, for use as electronic evidence. Certificates signed with the transient non-production key are marked unverifiable.
  • Auditor: read-only role with audit search and filters; reports and CSV exports run as background jobs.

4.8 Notifications and integration events

  • Templates per fiduciary (built-in text as fallback; English only for the newest alerts). Delivered as in-CMS notifications and email.
  • Webhooks (notification, purge, OTP): HMAC-SHA256 signed, with a delivery ID; retries at 1 m, 5 m, 30 m, 2 h, 12 h (six attempts); failures visible to the DPO for inspection and retry. Targets that resolve to private addresses are refused. Polling remains the reconciliation path.

4.9 DPO dashboard and consoles

Admin console: fiduciaries, apps, API keys, operators. DPO console: dashboard (pending purges, grievances, rights requests, breach clocks), policies, RoPA, principals and consent review, rights, grievances, compliance enforcement (search, legal holds, webhook deliveries, jobs), breach, audit, legal (certificates), reports, settings, team. Console pages are served only after a server-side session check. A BRAND_NAME setting white-labels the UI.

5. Technical design

5.1 Stack

DatabasePostgreSQL 15 (pgcrypto), HikariCP pool (15), ordered, re-runnable migrations (28 at v0.6) in db/.
Front endStatic HTML and JavaScript; no framework or build step. (v0.1's React plan was not adopted.)
Librariesjjwt (tokens), jbcrypt (passwords), OpenPDF (reports), dnsjava (DNS proof), JSON-schema validator, Jackson.
IntegrationREST/JSON, OpenAPI 3 spec (docs/api/openapi.yaml), signed webhooks, polling, JMeter load test, regression suite. SDKs are planned, not shipped.

5.2 Request path

Request → origin check → authenticate (operator JWT, App API key, or principal JWT) → function allowed for that credential → permission and tenant check → JSON-schema validation → service → audit event. Failures return generic errors with no schema detail. Client credentials: API key (X-API-Key) with scope, or principal token; PURGE functions are API-key only.

5.5 Deployment

  • Docker Compose: postgres_db (volume, health check) and jetty_app (port 8080). Settings come from .env; TSI_DPDP_CMS_ENV=production turns on the strict checks. A non-Docker install uses server/serve.sh.
  • Put behind TLS (reverse proxy) and set TRUSTED_PROXY; keep the database private, with SSL.
  • Backup: backup/backup.sh (database dump, reports, optional encrypted .env and keystore) and restore.sh (verify in a throwaway database). Offsite copy and scheduling are the operator's job.
  • Availability: single node is a single point of failure; mitigate with backups and an offsite restore. Several app instances over one database are supported.
  • Upgrade: back up, apply db/18 to db/28 in order (re-runnable). v0.6 forces MFA enrolment in production and re-login.

7. Gaps and roadmap

What the code does not do today, ranked within each group (mirrored in docs/plan/gaps.md). Ratings are a feature-level reading, not legal advice; counsel should confirm provisions and commencement dates.

7.1 DPDP Act coverage gaps

Core consent management is rated good. Overall coverage is partial by design: much of the Act (securing the fiduciary's own systems, data accuracy, processor contracts, DPIA, audits, cross-border rules) is organisational, and the CMS supports it with records only.

7.4 What the CMS cannot do, and does not claim

Secure the fiduciary's own systems; verify a parent's or a principal's identity; erase data inside processors' systems (it tracks the request and the processor's confirmation, and the count is a claim); produce the personal data for an access request; decide the lawful basis; submit anything to the Board; or make an organisation compliant. The CMS supports compliance and provides evidence.
