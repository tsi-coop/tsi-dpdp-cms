The client API for Data Fiduciaries and Data Processors integrating consent capture, processing validation, the rights/dashboard, grievances, notifications, and the purge lifecycle into their own backend stacks.

Read this alongside the narrative guides, not instead of them: System Integration Guide, Webhook Integration Guide, Client Polling Integration Guide. This document is the machine-readable companion; the guides carry workflow context (the purge lifecycle timing, webhook signing, etc.) that doesn't belong in a schema.

Routing model (read before using this spec)

This is an RPC-style API, not resource-per-URL REST: every call is POST to one of five fixed base paths, and the JSON body's _func field - not the URL - selects the operation. Anything appended to a base path (e.g. /api/v1/client/consent/validate) is parsed but discarded by the router.

Because of this, each path below documents its operation's request body as a oneOf discriminated on _func; pick the schema matching the function you're calling. This is the most faithful way to model the real dispatch behavior in OpenAPI, but tooling that expects one URL per operation (client generators, some "try it" UIs) may not reflect that as cleanly as a REST API would - if your tooling struggles with the discriminated union, treat each x-tsi-...-tagged schema as the effective single-operation contract for that function.

Ground truth

Every request/response field and error condition below was verified directly against the service source (src/org/tsicoop/dpdpcms/service/v1/{Policy,Consent,Grievance,Notification,Compliance}.java) and InterceptingFilter.java, not just the guides. Several real discrepancies between the guides' examples and actual server behavior surfaced during that verification and are called out explicitly below (e.g. record_consent silently ignoring policy_version/ip_address/ timestamp/jurisdiction; two functions whose own 400 error message names the wrong field). Where source and guide disagree, source wins and the guide should be treated as needing a follow-up correction.

Policy

Notice content - the published, multilingual consent policy.

Policy operations (list_active_policies / get_policy / get_active_policy)

Known inconsistency vs. the System Integration Guide: the guide states get_active_policy is "the exception" requiring an explicit fiduciary_id in the body. In source, list_active_policies also requires it explicitly for every caller - unlike every function in /consent, /grievance, /notification, and /compliance, this file never falls back to resolving fiduciary_id from the API key or from a Principal JWT's stamped request attribute. A Principal-JWT caller who omits it from the body gets a 400, not an automatic resolution.

Consent

Consent capture, validation, rights/dashboard reads, withdrawal, and erasure.

Consent operations (record_consent / record_parent_consent / get_active_consent / get_consent_record_details / list_consent_history / link_user / validate_consent / withdraw_consent / erasure_request)

Unlike /policy, every function here resolves fiduciary_id automatically when omitted from the body: body value, else the Principal JWT's stamped fiduciary, else the calling App's own fiduciary (via X-API-Key/X-API-Secret). So for API-key or Principal-JWT callers, fiduciary_id is effectively optional everywhere in this operation.

Principal-JWT guard: if authenticated via Bearer JWT, the user_id in the body must match the token's subject, or the call is rejected with 403 regardless of which function was requested.

Grievance

Section 13 grievance submission and lookup.

Grievance operations (submit_grievance / get_grievance / list_user_grievances)

Same Principal-JWT user_id-match guard as /consent applies here.

Undocumented in the guide: type is accepted as free text and stored verbatim - the server does not validate it against any enum. The rights-portal UI itself only ever sends one of GENERAL_COMPLAINT, ERASURE_REQUEST, DATA_ACCESS_REQUEST, CORRECTION_REQUEST; only ERASURE_REQUEST changes behavior (7-day SLA instead of the 30-day default).

Notification operations (list_notifications / mark_notification_read)

See the Client Polling Integration Guide for the recommended polling pattern, and the Webhook Integration Guide for the equivalent push events.

Known issue, not yet fixed: if the body omits fiduciary_id, the server falls back to UUID.fromString(apiKey) without first checking whether an API key header was even sent. A Principal-JWT caller (no X-API-Key header) who also omits fiduciary_id from the body will hit a null-pointer path that surfaces as a generic 500, not a clean 400. Always pass fiduciary_id explicitly from a Principal-JWT context until this is fixed.

Compliance

Purge-request polling and confirmation (PURGE scope; API key only).

Purge-lifecycle operations (list_purge_requests / update_purge_status)

PURGE scope, API key only. Both functions here require the PURGE permission scope, which is unconditionally rejected over a Principal JWT (see principalBearerAuth) - this path is only reachable with X-API-Key/X-API-Secret, hence the operation-level security override above.

Authorization gap, already known and documented in the guide: update_purge_status does not check that the request being updated belongs to your fiduciary. Any valid PURGE-scoped API key can update any fiduciary's purge request by id. Only ever call this with an id your own App actually received from list_purge_requests or a purge_request_created webhook - never construct or guess one.
